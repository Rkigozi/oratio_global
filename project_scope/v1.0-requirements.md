# Oratio v1.0 — Requirements Document

**Status:** Final Draft — Locked for v1.0  
**Last Updated:** 2026-06-10  
**Target Release:** Aug 11, 2026  
**Platform:** PWA (installable web app)  
**Post-v1.0:** Native mobile app (React Native) planned

---

## 1. Product Overview

Oratio is a global Christian prayer platform that connects people through shared prayer.

**Core promise:** See prayers from around the world. Pray for others. Feel connected to a global community of faith.

**Target audience:** Christians of all ages who want to pray with and for others, especially those without access to a local faith community.

**Key constraint:** Privacy-first — never store exact locations, never expose users in sensitive regions.

## 2. User Personas

| Persona | Demographics | Needs | Frustrations |
|---------|-------------|-------|-------------|
| **The Isolated Believer** (Rachel) | 50+, has faith community but sees the potential for those who don't | Connection, being prayed for, praying for others | App not loading, can't find what she needs |
| **The Prayer Warrior** (Naomi) | 30+, active in church, wants depth | Specific categories, pray-for-region, sense of global unity | Categories too broad, can't target prayers |

## 3. Core User Journey

```
Discover (landing) → Install (PWA prompt) → Onboard → Browse Map/Feed
→ Search/Filter → Read prayer → Pray → Comment → Submit prayer
→ Return next day → Notification (someone prayed/commented) → Re-engage
```

## 4. Feature Requirements

### 4.1 Foundation (Sprint A — Jun 16-30)

#### F-001: Supabase Backend Setup
**User story:** As a user, I want my prayers, profile, and interactions to persist across sessions so I can return to my prayer journey.

**Dependencies:** None

**Acceptance criteria:**
- Supabase project created with production-ready config
- Database tables: `users`, `prayer_requests`, `prayer_interactions`, `comments`, `reports`
- Row-level security policies defined for all tables
- Migration scripts versioned in the repo
- Environment variables configured (VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)

---

#### F-002: REST API for Prayer CRUD
**User story:** As a developer, I need API endpoints to create, read, update, and delete prayers.

**Dependencies:** F-001

**Acceptance criteria:**
- Endpoints: POST /prayers, GET /prayers, GET /prayers/:id, DELETE /prayers/:id
- Pagination and filtering (by category, location) supported
- Rate limiting on POST endpoint
- Consistent error response format

---

#### F-003: Authentication
**User story:** As a user, I want to sign up with email or Google so my data is mine and persists.

**Dependencies:** F-001

**Acceptance criteria:**
- Email/password sign-up and sign-in
- Google OAuth sign-in
- Anonymous opt-in (use app without account, prompt to create account later)
- Session persistence across browser close
- Sign-out from profile
- Password reset flow

---

#### F-004: PWA Manifest
**User story:** As a user, I want to add Oratio to my home screen so it opens like a real app.

**Dependencies:** None

**Acceptance criteria:**
- Web App Manifest with icons (192px, 512px), theme colour, background colour
- `display: standalone` — opens full-screen, no browser chrome
- `start_url` set to landing page
- Splash screen generated from manifest
- Manifest validates with Lighthouse PWA audit

---

#### F-005: Service Worker Skeleton
**User story:** As a user, I want the app to load fast even on slow connections.

**Dependencies:** None

**Acceptance criteria:**
- Service worker registered on first visit
- Cache-first strategy for static assets (JS, CSS, images)
- Stale-while-revalidate for API responses
- Graceful update flow (skip waiting + prompt to refresh)

---

#### F-006: Fix Landing Page Scroll Freeze (iOS 18 / iPhone 15)
**User story:** As an iPhone 15 user, I want the landing page to scroll so I can use the app.

**Dependencies:** None

**Acceptance criteria:**
- Landing page scrolls on iPhone 15 in both Safari and Chrome
- Tested on iOS 18+ with both mobile Safari and Chrome
- No regressions on other devices
- Root cause identified and fixed (likely 100dvh + overflow interaction)

---

### 4.2 Core Loop + Comments (Sprint B — Jun 30-Jul 14)

#### CL-001: Comments (Reddit-style)
**User story:** As a user, I want to leave a written response on someone's prayer to encourage them, not just tap a button.

**Dependencies:** F-001, F-002, F-003

**Acceptance criteria:**
- `comments` database table: id, prayer_id, user_id, parent_id (nullable), body, created_at
- CRUD API endpoints for comments
- Comment count displayed on prayer feed cards
- Tap comment button opens comment sheet/drawer
- Top-level comments + single-level replies (reply to a comment)
- Reply button on each comment opens inline composer
- Delete own comment
- Report a comment
- No nested threading beyond 1 level (for v1.0)

---

#### CL-002: Comment Notifications
**User story:** As a prayer submitter, I want to know when someone comments on my prayer so I feel supported.

**Dependencies:** CL-001, CL-003

**Acceptance criteria:**
- Prayer submitter receives push notification when someone comments
- Comment author receives push notification when someone replies to their comment
- Notification includes prayer preview + comment preview
- Tap notification opens the prayer with comment thread visible
- Notification dot/badge in app

---

#### CL-003: Push Notifications Infrastructure
**User story:** As a user, I want the app to notify me even when I'm not using it.

**Dependencies:** F-004, F-005

**Acceptance criteria:**
- FCM / Web Push API integration
- Permission prompt (timed, not on first visit — ask after value demonstrated)
- Subscribe/unsubscribe in profile settings
- Notification types: new comment on your prayer, reply to your comment, someone prayed for your prayer

---

#### CL-004: Comments Moderation
**User story:** As a community member, I want inappropriate comments to be removable so the space stays respectful.

**Dependencies:** CL-001

**Acceptance criteria:**
- Report comment flow (three-dot menu → select reason → confirm)
- Reported comments logged in database with reason + timestamp
- Admin delete comment capability
- No pre-approval queue for v1.0 (v1.1 feature)

---

#### CL-005: Performance Optimization
**User story:** As a user, I want the app to load fast so I don't wait around.

**Dependencies:** None

**Acceptance criteria:**
- Route-level code splitting (lazy load pages)
- Bundle analysis run — total JS bundle under 200KB (gzipped)
- Cold start < 3s on mobile 3G
- Lighthouse performance score > 80

---

#### CL-006: Contrast / Readability Fix
**User story:** As an older user, I want to read prayer text without straining my eyes.

**Dependencies:** None

**Acceptance criteria:**
- Relative time labels ("30d ago") match brightness of city/location text
- Prayer card backgrounds checked for WCAG AA contrast compliance
- Base font size verified at minimum 16px
- All text visible on device at 50% brightness

### 4.3 Discovery + Polish (Sprint C — Jul 14-28)

#### DP-001: Search Bar
**User story:** As a user, I want to search for prayers by keyword, location, or topic so I can find what matters to me.

**Dependencies:** F-001, F-002

**Acceptance criteria:**
- Search input in feed header
- Searches across: prayer text, category, location (city + country)
- Results update as user types (debounced, 300ms)
- Empty state: "No prayers found for [query]"
- Clears filters visually

---

#### DP-002: Category Redesign
**User story:** As a user, I want categories that match what I'm actually praying about — not broad buckets that don't fit.

**Dependencies:** F-001

**Acceptance criteria:**
- Current broad categories replaced with sub-categories or tag system
- Option A (preferred): Flat tag system — multiple tags per prayer (e.g. "Healing: Physical", "Healing: Emotional", "Family: Parenting", "Family: Marriage")
- Category/tag picker on submit form updated
- Filter by tag on feed
- Tags visible on prayer cards
- Backward compatibility: existing prayers with old categories mapped to new system

---

#### DP-003: Map Visual Refresh
**User story:** As a user, I want the map to be beautiful and readable, not just a dark blob.

**Dependencies:** None

**Acceptance criteria:**
- Map tile layer evaluated — lighter option considered (test both dark + semi-light)
- Clearer country borders
- Optional: colour gradient on markers indicating density or recency
- No performance regression (still smooth zoom/pan)

---

#### DP-004: Translation
**User story:** As a user whose first language isn't English, I want to read prayers in my language.

**Dependencies:** None

**Acceptance criteria:**
- Integration with translation API (Google Cloud Translation or DeepL)
- "Translate" button on each prayer card
- Toggle between original and translated text
- Language auto-detection on prayer content
- Translation cache (localStorage or backend) to avoid repeat API calls
- User language preference in profile settings (default: browser locale)
- No auto-translate on feed load — only on explicit button tap (cost control)

---

#### DP-005: PWA Offline Support
**User story:** As a user, I want to read previously loaded prayers even when I don't have internet.

**Dependencies:** F-005

**Acceptance criteria:**
- Prayer feed cache for offline reading
- Map tiles cached for offline viewing
- Graceful offline state: "You're offline — showing prayers from earlier"
- Submit button disabled with message when offline

---

#### DP-006: Install Prompt
**User story:** As a first-time user, I want a simple way to get the app on my home screen without figuring it out myself.

**Dependencies:** F-004

**Acceptance criteria:**
- Timed prompt (appears after user submits first prayer OR after 3rd visit)
- Android: Native beforeinstallprompt event captured, custom styled banner shown
- iOS: Step-by-step overlay ("Tap Share → Add to Home Screen → Add") with screenshots
- Prompt is dismissible ("Not now, maybe later")
- Prompt doesn't reappear after dismissal for 7 days
- Detects if already installed (standalone mode) and suppresses

---

#### DP-007: Save Button UX
**User story:** As a user, I want a clear, obvious way to save a prayer to pray for later.

**Dependencies:** None

**Acceptance criteria:**
- Save/bookmark button more prominent on prayer cards (icon + label or large touch target)
- Visual feedback on save (icon fill animation)
- Saved prayers appear in profile's saved section
- Existing saved prayers function works without regression

---

#### DP-008: Shareable Link
**User story:** As a user, I want to share a prayer with a friend after I submit it.

**Dependencies:** F-001, F-002

**Acceptance criteria:**
- After successful prayer submission, a share button generates a shareable link
- Link opens the specific prayer in the feed
- Native share sheet on mobile, clipboard copy on desktop
- Link works for users who haven't signed up (opens prayer, then prompts to join)

### 4.4 Launch Readiness (Sprint D — Jul 28-Aug 11)

#### LR-001: CI/CD Pipeline
**User story:** As a developer, I want automated deployment so every commit doesn't require manual upload.

**Acceptance criteria:**
- GitHub Actions workflow for build + deploy to Netlify
- Preview deploys on PR branches
- Production deploy on merge to main
- Build fails on TypeScript errors

---

#### LR-002: Error Monitoring (Sentry)
**User story:** As a developer, I want to know when the app breaks so I can fix it before users are impacted.

**Acceptance criteria:**
- Sentry SDK integrated into React app
- Error boundaries at route level
- Unhandled promise rejections captured
- Source maps uploaded for readable stack traces
- Performance tracing for critical flows

---

#### LR-003: Basic Analytics (PostHog)
**User story:** As a product owner, I want to know how people use the app so I can make better decisions.

**Acceptance criteria:**
- PostHog or similar privacy-friendly analytics
- Events tracked: prayer submitted, prayer prayed for, comment left, search performed, user signed up, app installed
- Dashboard with weekly active users, retention, top categories
- No personally identifiable information sent to analytics

---

#### LR-004: Critical Path Tests
**User story:** As a developer, I want confidence that the core flow works after every change.

**Acceptance criteria:**
- Test: User can submit a prayer
- Test: User can tap "I Prayed" and see count increment
- Test: User can comment on a prayer
- Test: Feed loads and displays prayers
- Test: User can search and see results
- Test: Auth sign-up and sign-in flow

---

#### LR-005: Accessibility Audit
**User story:** As a user with visual impairment, I want the app to work with screen readers and have sufficient contrast.

**Acceptance criteria:**
- ARIA labels on all interactive elements
- Keyboard navigation works for all features
- Colour contrast ratios meet WCAG AA minimum
- Focus indicators visible on all interactive elements
- Tested with VoiceOver (iOS) and TalkBack (Android)

---

#### LR-006: Landing Page Clarity
**User story:** As a first-time visitor, I want to immediately understand what Oratio is and why I should use it.

**Acceptance criteria:**
- Tagline: "Pray together. Anywhere." (or final version)
- 1-2 sentence mission statement above the fold
- Three feature highlights (Map, Submit, Pray)
- Beta/prototype transparency notice ("Oratio is in beta — your feedback shapes the future")
- Clear CTA: "Start Praying" (new user) / "Sign In" (returning)

---

#### LR-007: Church Launch Collateral
**Acceptance criteria:**
- One-page install flyer (screenshots of each install step for iOS + Android)
- Demo script for projector walkthrough
- Helpers brief (how to assist users during launch service)

## 5. Data Model (Key Entities)

```
users
├── id (uuid, PK)
├── username (text, unique)
├── email (text, nullable)
├── auth_provider (text — 'email' | 'google' | 'anonymous')
├── display_name (text, optional)
├── avatar_url (text, optional)
├── language_preference (text, default: browser locale)
├── created_at (timestamp)
└── updated_at (timestamp)

prayer_requests
├── id (uuid, PK)
├── user_id (uuid, FK → users)
├── body (text, max 500 chars)
├── category (text — main category)
├── tags (text[] — sub-categories / tags)
├── location_city (text)
├── location_country (text)
├── location_lat (float, approximate)
├── location_lng (float, approximate)
├── is_anonymous (boolean)
├── prayer_count (integer, default 0)
├── is_answered (boolean, default false)
├── answered_at (timestamp, nullable)
├── created_at (timestamp)
└── updated_at (timestamp)

prayer_interactions
├── id (uuid, PK)
├── user_id (uuid, FK → users)
├── prayer_id (uuid, FK → prayer_requests)
├── created_at (timestamp)
└── UNIQUE(user_id, prayer_id)

comments
├── id (uuid, PK)
├── prayer_id (uuid, FK → prayer_requests)
├── user_id (uuid, FK → users)
├── parent_id (uuid, FK → comments, nullable)
├── body (text, max 500 chars)
├── created_at (timestamp)
└── updated_at (timestamp)

reports
├── id (uuid, PK)
├── reportable_type (text — 'prayer' | 'comment')
├── reportable_id (uuid)
├── reported_by (uuid, FK → users)
├── reason (text)
├── status (text — 'pending' | 'resolved' | 'dismissed')
├── created_at (timestamp)
└── resolved_at (timestamp, nullable)

push_subscriptions
├── id (uuid, PK)
├── user_id (uuid, FK → users)
├── endpoint (text)
├── keys (jsonb)
├── created_at (timestamp)
└── updated_at (timestamp)
```

## 8. Out of Scope (v1.0)

These are explicitly deferred to v1.1+:

| Feature | Rationale |
|---------|-----------|
| Native mobile app (React Native) | PWA first to validate; native planned post-v1.0 |
| @mentions in comments | Reply button covers the need with simpler infra |
| Answered prayer / testimonies | Adds new content type — v1.1 candidate |
| Light/dark mode | Polish, not essential |
| Pray-for-region | Requires data model change + map rework |
| Trending by region | Needs search infra and aggregation — v1.1 |
| Prayer groups / communities | Out of scope for v1.0 |
| Donate | Feature request, not in product vision |
| Full moderation dashboard | Report + admin delete is sufficient for v1.0 |
| Real-time updates (prayer feed, live counts) | v1.1 performance enhancement |
